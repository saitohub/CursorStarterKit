やらかした。

GitHubにpushしようとしたら、こんなエラーが出て弾かれた。

> Push cannot contain secrets — Google OAuth Access Token detected

「シークレット（機密情報）が含まれているのでpushできません」という意味だ。GitHubのセキュリティ機能「Push Protection」が作動した。

最初は意味がわからなかった。「どこに？」と思いながらエラーを読むと、`token.json` の中にGoogleのOAuthトークンが含まれていると書いてある。

そこで気づいた。ObsidianのVaultをまるごとGitで自動バックアップしていて、GmailのAPIを使うために置いていた認証ファイルが何ヶ月もコミットされ続けていたのだ。

## AIと一緒に作業していたら、問題が見えてきた

今回の話の出発点は「AIを使った自動化」だ。GmailからデータをCSVに書き出すPythonスクリプトを書いていて、それをClaude Codeと一緒に動かしていた。

AIと作業しながらファイルをいじり、スクリプトを直し、「よし動いた」とpushしようとしたら止まった。機密情報が混入していたからだ。

ここで気づいたのは、**AIを使って作業を速くすればするほど、セキュリティの確認を飛ばしやすくなる**ということだ。「ポンポンと進めてしまいそうで怖い」という感覚は、このときにはっきりした。

## 「APIの認証ファイル＝個人情報」という認識が薄かった

問題のファイルは2種類。

- **`token.json`** — Googleへのアクセストークン。これがあれば自分のGmailにアクセスできる
- **`client_secret_*.json`** — Google OAuthのクライアントID・シークレット。漏れると第三者が自分のGoogle APIを使えるようになる

どちらも「個人情報」だ。ただ、名前や住所と違って、ファイルを見ただけでは「これが個人情報だ」と実感しにくい。

そこを甘く見ていた。`.gitignore` に書いていなかったから、自動バックアップのたびに何ヶ月もコミットされ続けていた。

**今やっていることと何が同じか、を考えながら覚えていく必要がある。** APIキーを扱うのは、SNSのパスワードをメモして共有フォルダに置くのと本質的には同じだ。ファイルが機械語っぽく見えるだけで、やっていることは変わらない。

## どうやって直したか

### 手順1：`.gitignore` に追記

```
token.json
client_secret*.json
```

ただし、これは「今後は無視する」設定だ。すでにコミット済みのファイルは消えない。

### 手順2：git の履歴から除去

`git filter-branch` を使って、未pushの8コミット全部から認証ファイルを削除した。

```bash
git filter-branch --force --index-filter \
  'git rm --cached --ignore-unmatch token.json' \
  HEAD~8..HEAD
```

これで「token.jsonを追加したコミット」が書き換えられ、履歴上は存在しなかったことになる。

### 手順3：2回やる羽目になった

pushしたら今度は `client_secret_*.json` でも弾かれた。同じ手順でもう一度。

> **反省点**：認証ファイルは複数あることが多いので、最初にまとめて確認すべきだった。

### 手順4：認証ファイルをVault外に移動

```
~/secrets/gmail_api/client_secret_*.json
~/secrets/gmail_api/token.json
```

Vault外のGit管理外フォルダに移して、スクリプトの参照先も変更。これで以後は混入しない。

### 手順5：force push

履歴を書き換えたので `git push --force` が必要だった。これで通った。

## Claude Codeへの移行中に気づいたこと

今はCursorからClaude Codeへ移行しているところだ。Claude Codeはまだ「育っていない」状態で使い始める。

具体的には、最初のうちは操作のたびに「これを実行していいですか？」という確認が何度も出てくる。`git` コマンド1本打つたびに承認が必要、なんてこともある。

だから「こういうコマンドは全部やっていいよ」という権限設定を入れながら進めることになる。これがClaude Codeを使い始めるときの地味な面倒くささだ。

ただ逆に言えば、**最初にそのひと手間をかけることで、AIが何をやっているかを意識させられる**という側面もある。「全部OK」にする前に、「これは本当に全部OKにしていいのか」と一度考える機会になる。

今回のセキュリティ事故はまさにその「考える機会」を飛ばしたことが原因だった。

## まとめ

- **Vault（Obsidian）をGit管理しているなら、`.gitignore` の設定が最初の一歩**
- 認証ファイルはVault外（`~/secrets/` など）に置く。最初からそうするだけでいい
- やらかしても `git filter-branch` で履歴から消せる。ただしforce pushが必要
- **「今やっていることは何と同じか」を考える習慣が、セキュリティ事故を防ぐ**

AIを使って作業を速くするのはいい。ただ、速くするほど「確認を飛ばす」リスクも上がる。Claude Codeの権限確認が最初は面倒に感じたが、あれは「本当にいいのか」を問いかける仕組みでもあった。

---

Claude Codeと一緒に対処した。エラーの原因特定・git filter-branchの実行・スクリプトの修正・認証ファイルの移動まで、ターミナルをほぼ触らずに済んだ。途中でいくつかミスもあったが、1時間以内に全部解決できた。

「何が起きているかわからない」状態から始まったが、AIと一緒に動かすことでエラーの意味が見えてきた。こういう「わからないエラーへの対処」こそ、AIが役立つ場面だと思う。ただし、そのAIに何を渡しているかは、自分で意識しておく必要がある。
